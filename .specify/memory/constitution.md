# ad-click-event Constitution

## Core Principles

### I. 이벤트 무손실

- 수집 API는 이벤트가 내구성 있는 저장소(또는 큐)에 기록된 뒤에만 성공을 응답해야 한다 (MUST).
- 처리에 실패한 이벤트는 재시도하고, 재시도 한도를 넘으면 격리 저장소(DLQ)로 옮겨야 한다 (MUST).
  어떤 단계에서도 이벤트를 조용히 버려서는 안 된다.
- "수신 수 = 집계 반영 수 + DLQ 수 + 중복 제거 수"를 대조할 수 있어야 한다 (MUST).

**근거**: 클릭 하나하나가 광고비·성과 집계와 직결되므로, 유실은 곧 잘못된 숫자다.

### II. 중복 제거·멱등성

- 모든 클릭 이벤트는 고유 식별자(`event_id`)를 가져야 한다 (MUST).
- 무손실을 위해 이벤트는 최소 한 번(at-least-once) 전달되므로, 같은 `event_id`는 집계에 정확히
  한 번만 반영되어야 한다 (MUST).
- 수집·적재·집계의 모든 단계는 같은 입력을 다시 실행해도 같은 결과를 내야 한다 (MUST).
  재처리(backfill)는 언제든 안전해야 한다.
- 중복을 판단하는 기간(dedup window)은 각 기능 스펙에 명시해야 한다 (MUST).

**근거**: 원칙 I의 재시도는 중복을 만든다. 중복 제거가 없으면 무손실이 과다 집계로 바뀐다.

### III. 이벤트 스키마 계약

- 이벤트 형식은 정의 파일(Avro·Protobuf·JSON Schema 중 plan 단계에서 선택)로 저장소에 두고
  버전을 매겨야 한다 (MUST).
- 선택(optional) 필드 추가는 같은 메이저 버전 안에서 허용한다. 필드 삭제·이름 변경·타입 변경·
  선택 필드의 필수화는 새 메이저 버전으로만 해야 하며, 기존 버전은 소비자가 옮겨갈 때까지
  함께 지원해야 한다 (MUST).
- 수집 시점에 스키마를 검증하고, 위반 이벤트는 버리지 않고 격리 저장소로 보내야 한다 (MUST).
- 스키마 호환성 검사는 CI에서 자동으로 실행해야 한다 (MUST).

**근거**: 수집과 집계가 같은 계약을 보게 해서, 한쪽 변경이 다른 쪽을 몰래 깨뜨리지 않게 한다.

### IV. 개인정보 최소수집

- 이벤트에 담는 필드는 집계·기능 스펙에 필요한 것만이어야 하며, 필요한 이유를 스키마 또는
  스펙에 기록해야 한다 (MUST).
- IP·기기 정보 등 개인을 식별할 수 있는 필드는 스키마에서 개인정보 필드로 표시해야 한다 (MUST).
- 현재 단계에서는 실제 사용자 데이터를 수집하지 않고 테스트·합성 데이터만 다루므로, 개인정보
  필드의 원본 값을 그대로 저장하는 것을 허용한다.
- 실제 사용자 데이터를 수집하기 전에 이 원칙을 개정해 해시·마스킹 방식과 보존 기간을 정해야
  한다 (MUST). 개정 전에는 실데이터 수집 기능을 머지할 수 없다.

**근거**: 지금은 개발 편의를 우선하되, 개인정보 필드를 미리 표시해 두면 실데이터 전환 시
처리 대상을 바로 찾을 수 있다.

### V. 테스트 우선 (NON-NEGOTIABLE)

- 구현 전에 테스트를 먼저 작성하고, 실패를 확인한 뒤 구현한다 (Red-Green-Refactor) (MUST).
- 테스트 없이 동작을 바꾸는 변경은 머지할 수 없다 (MUST).
- 원칙 I–III은 각각 전용 테스트를 가져야 한다 (MUST): 재시도·장애 주입 시 유실 없음,
  같은 이벤트 중복 전송 시 한 번만 집계, 스키마 하위 호환성.

**근거**: 유실·중복·스키마 깨짐은 운영 중에 발견하면 이미 숫자가 틀린 뒤다.

### VI. 관측성

- 로그는 구조화된 형식으로 남기고, 단계 간 추적을 위해 `event_id`를 포함해야 한다 (MUST).
- 각 처리 단계는 최소한 수신 수, 처리 성공 수, 재시도 수, DLQ 수, 중복 제거 수,
  처리 지연(end-to-end lag)을 지표로 내보내야 한다 (MUST).

**근거**: 원칙 I·II가 실제로 지켜지는지는 숫자로만 확인할 수 있다.

### VII. 성능 목표 명시

- 각 기능 스펙은 처리량(초당 이벤트 수)과 지연(p95·p99) 목표를 숫자로 적어야 한다 (MUST).
  "빠르게" 같은 숫자 없는 표현은 목표로 인정하지 않는다.
- 기능 완료 전에 부하 테스트로 목표를 검증하고 결과를 기록해야 한다 (MUST).

**근거**: 클릭 트래픽은 몰릴 때 몰리므로, 목표가 숫자로 없으면 설계 판단의 기준도 없다.

### VIII. 단순성 우선

- 현재 스펙이 요구하는 것만 만든다 (YAGNI) (MUST).
- 새 인프라 구성요소(저장소·메시지 브로커·프레임워크)나 추상화 계층을 추가하려면, plan.md의
  Complexity Tracking 표에 필요한 이유와 더 단순한 대안을 기각한 이유를 적어야 한다 (MUST).

**근거**: 개인 프로젝트이므로 운영·유지보수 부담이 곧 진행 속도를 결정한다.

## 기술 제약

- 백엔드(수집·저장·판정·집계·서빙 API와 데이터 생성기) 코드와 그 테스트는 Kotlin으로만 작성한다
  (MUST). Java 소스 파일은 추가하지 않으며, Java 라이브러리·프레임워크 사용은 허용한다.
- 브라우저에서 도는 웹 화면(시각화 등) 코드와 그 테스트는 TypeScript로 작성한다 (MUST). 일반
  JavaScript 소스는 추가하지 않는다. 웹 화면은 백엔드가 공개한 API·지표만 읽고, 도메인 규칙(판정·
  집계)을 다시 구현하지 않는다 (MUST).
- 원칙 I–VIII은 언어와 관계없이 웹 화면 코드에도 똑같이 적용된다.
- 런타임은 JVM이다. JVM 버전, 빌드 도구, 스키마 형식, 메시지 브로커, 저장소는 `/speckit-plan`
  단계에서 결정하고 근거를 plan.md에 기록한다.
- 현재 다루는 데이터는 테스트·합성 데이터뿐이다 (원칙 IV 참조).

## 개발 흐름·품질 게이트

- 기능 작업은 `/speckit-specify` → (`/speckit-clarify`) → `/speckit-plan` → `/speckit-tasks` →
  `/speckit-implement` 순서로 진행한다.
- plan.md의 Constitution Check를 통과하기 전에는 tasks를 만들지 않는다 (MUST). 위반이 불가피하면
  Complexity Tracking 표에 정당화해야 한다.
- main 브랜치에 직접 push하지 않는다. 모든 변경은 PR로 올린다 (MUST).
- PR 본문에 원칙 I–VIII 셀프 체크리스트를 채우고, CI(빌드·테스트·스키마 호환성 검사)가 통과해야
  머지한다 (MUST). 개인 프로젝트이므로 다른 리뷰어의 승인은 요구하지 않는다.

## Governance

- 이 헌법은 다른 개발 관행·습관보다 우선한다.
- **개정 절차**: 개인 프로젝트이므로 프로젝트 오너가 단독으로 결정한다. 개정은
  `/speckit-constitution`으로 하고, 변경 이유를 PR에 남기며, 버전과 Last Amended 날짜를 갱신한다.
- **버전 정책** (Semantic Versioning):
  - MAJOR: 원칙 삭제 또는 기존 원칙을 호환되지 않게 재정의
  - MINOR: 원칙·섹션 추가 또는 지침의 실질적 확대
  - PATCH: 문구 명확화, 오탈자 수정 등 의미 변화 없는 수정
- **준수 확인**: 기능마다 plan 단계의 Constitution Check에서, 변경마다 PR 셀프 체크리스트에서
  확인한다. 실제 사용자 데이터 수집 계획이 생기면 그 작업보다 먼저 원칙 IV를 개정한다.
